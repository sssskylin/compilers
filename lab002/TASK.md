
# Задача A. Избавьтесь от легаси или продолжайте жить в проклятом мире, который сами создали

**Легенда:** Вы — инженер команды системного программирования и продолжаете изучать доставшиеся вам "в наследство" от бывшего сотрудника компании модули. Ваше внимание привлёк модуль `legacy`, который потребляет слишком много памяти и странно линкуется с новым патчем `hotfix`. К сожалению, исходный код модуля `legacy` был утерян и написать его заново сейчас нет возможности, но у ваших коллег сохранились некоторые артефакты сборки...
**Требования к окружению:** Linux/WSL, binutils (`nm`, `readelf`, `size`, `objdump`, `strings`).
**Формат сдачи:** Текстовый файл с ответами на вопросы и выводом команд.
**Дано:**

1. Файл `hotfix.o` и его исходный код `hotfix.c`:

```c
char system_mode[4];

void apply_hotfix(void) {
  system_mode[0] = 'A';
  system_mode[1] = 'B';
  system_mode[2] = 'C';
  system_mode[3] = '\0';
}
```

2. Файлы `main.o`, `legacy.o` и `core.o` без исходного кода.

**Замечание:** если будете собирать `hotfix.o` самостоятельно, делайте это с флагом `-fcommon`, чтобы воспроизвести классическое поведение `gcc`.

---

### Задание

Ваша задача — выполнить анализ объектных файлов с помощью утилит `binutils`, найти аномалии в размещении данных и предотвратить потенциальную ошибку компоновки при добавлении нового модуля.

#### Этап 0. Базовый анализ размеров файлов и секций

> Используйте утилиту `size` для всех полученных файлов.

**Вопросы:**
1. В качестве ответа на этот вопрос предоставьте вывод команды `size`.
2. В одном из файлов столбец `bss` имеет аномально большое значение при малом общем размере файла (`dec`). Объясните, почему так могло произойти и где физически хранится содержимое этой секции на диске.

#### Этап 1. Извлечение строк

Исследуйте секции файла `core.o` с помощью `readelf`, а затем извлеките из него все печатаемые строки.

*Подсказка:* вы можете продолжать использовать консольные утилиты или задействовать инструменты для чтения бинарных файлов (например, расширение Hex Editor для Vscode).

**Вопросы:**
3. В файле `core.o` присутствует секция, которой нет в `legacy.o` и `hotfix.o` (интуиция подсказывает вам, что это что-то связанное со строками). Найдите её и укажите точное имя.
4. Найдите среди полученных строк секретный токен, оставленный разработчиком. Скопируйте его в отчёт.

#### Этап 2. Извлечение символов

Получите таблицы символов для всех файлов с помощью утилиты `nm`.

**Вопросы:**
5. Сравните таблицы символов четырёх файлов. Найдите имена, которые встречаются более чем в одном файле. Какие именно имена являются общими для нескольких модулей? *Подсказка:* особое внимание уделите символу `system_mode`. 
6. Для каждого общего имени проанализируйте:
    - В каких файлах оно присутствует?
    - Какой тип символа (буква во второй колонке `nm`) в каждом файле?
    - В какой секции (Ndx) оно находится?

_Подсказка:_ буква `D` означает определённый символ в секции `.data`, буква `C` — COMMON-символ (неинициализированная глобальная переменная, слабое определение).

7. Сопоставьте ваши наблюдения с исходным кодом `hotfix.c`, который вам доступен. В `hotfix.c` объявлена переменная `char system_mode[4];`. Что вы можете сказать о переменной `system_mode` в `core.o` и `legacy.o`, не имея их исходного кода? Какой конфликт это создаёт?

#### Этап 3. Попытка компоновки

Попробуйте скомпоновать исполняемый файл, передав все четыре объектных файла. Используйте флаг `-fcommon`, чтобы воспроизвести классическое поведение компоновщика.

```bash
gcc -fcommon core.o legacy.o hotfix.o main.o -o app
```

**Вопросы:**
8. Выдал ли компоновщик ошибку или предупреждение? Если да, процитируйте его дословно. Если нет, то, как вы думаете, почему компоновщик не сообщил о проблеме, несмотря на то, что `system_mode` определён в нескольких модулях с разными типами?

#### Этап 4. Анализ исполняемого файла и фикс

Исследуйте таблицу символов полученного исполняемого файла.

*Подсказка:*
```shell
nm app | grep system_mode
```

**Вопросы:**
9. В какой секции (`.data` или `.bss`) в итоге оказался `system_mode` в финальном исполняемом файле? Как вы думаете, почему компоновщик сделал именно такой выбор?

Современный стандарт разработки требует избегать слабых определений. Пересоберите проект, явно запретив `COMMON`-символы:

```bash
gcc -fno-common main.o hotfix.o legacy.o core.o -o app_better
```

**Вопросы:**
10. Какое сообщение об ошибке теперь выдает компоновщик? Как, не меняя имена переменных, можно исправить `hotfix.c`, чтобы эта сборка прошла успешно?
