# Задача A. Теория Большого взрыва

**Легенда:** вы — инженер команды, которая разрабатывает высоконагруженную систему симуляции физических процессов. В системе обрабатываются миллионы объектов: одни и те же поля регулярно читаются и изменяются в циклах физического расчёта, а другие нужны только в редких сценариях. После добавления многопоточности производительность неожиданно снизилась, а отдельные операции выполняются медленнее ожидаемого. 
Команда предполагает, что проблема связана не с алгоритмами, а с тем, как данные об элементарных частицах расположены в памяти. Вам предстоит проверить эту гипотезу экспериментально и подготовить рекомендации по изменению структур данных.

**Требования к окружению:** C++, Go или Rust; компилятор соответствующего языка. 
Для дополнительного задания необходимы Linux и `perf` с поддержкой `perf c2c`. 

**Формат сдачи:** файлы с исходным кодом экспериментов, текстовый файл с командами сборки и запуска, результатами измерений, ответами на вопросы и краткими выводами.

**Важно:** на каждое измерение проделайте 3–5 прогонов и фиксируйте медиану/минимум. 
Если эксперимент не подтверждает теорию, зафиксируйте это и предположите, почему так происходит (оптимизации компилятора, характеристики платформы и т.д.) 

Описание структуры для эксперимента с упаковкой:

```c
struct Mixed {
    char a;
    int b;
    char c;
    double d;
    short e;
};
```

Описание структуры частицы:

```c
struct Particle {
    float x, y, z;
    float vx, vy, vz;
    uint32_t color;
};
```

### Задание

Ваша задача — исследовать влияние выравнивания, упаковки и организации массивов структур на использование памяти и производительность. Для каждого эксперимента сначала сформулируйте прогноз, затем проведите измерения и объясните расхождения между ожидаемым и фактическим результатом.

#### Этап 1. Упаковка структур и выравнивание полей

Определите структуру `Mixed`, приведённую выше, дважды: в обычном виде и с принудительной упаковкой.

Для принудительной упаковки используйте соответствующий механизм языка:

- C: `#pragma pack(1)` или `__attribute__((packed))`;
- Rust: `#[repr(packed)]`.

Выведите размер обеих структур. Затем попробуйте получить адрес одного из полей упакованной структуры.

**Вопросы:**
1. Каковы размеры обычной и упакованной структур? Совпадает ли размер упакованной структуры с суммой размеров её полей?
2. Если вы получили предупреждение или сообщение об ошибке при попытке взять адрес, приведите его дословно. Почему чтение невыровненного поля через указатель может быть проблемой?

#### Этап 2. AoS и SoA

Реализуйте массив из достаточно большого количества (~10 миллионов на современных машинах, покрутите если не получается) частиц. Структура частицы задана выше и содержит координаты `x`, `y`, `z`, компоненты скорости `vx`, `vy`, `vz` типа `float` и цвет `color` беззнакового целочисленного типа (`u32` или `uint32_t` в `c++`).

Реализуйте шаг физического расчёта `x += vx`, `y += vy`, `z += vz` для всех частиц в двух вариантах организации данных:

- **AoS (Array of Structures):** массив структур `Particle`;
- **SoA (Structure of Arrays):** отдельные массивы для соответствующих полей частиц.

Измерьте время выполнения шага физического расчёта для обоих вариантов. Объясните результат с точки зрения использования кэш-линий.

**Вопросы:**
1. Какое время выполнения показал каждый вариант? Какое получилось ускорение SoA относительно AoS?
2. Сколько полезных байтов приходится на одну кэш-линию при обработке данных в каждом варианте? 
3. Почему при обработке массива SoA компилятору проще использовать SIMD-инструкции, чем при обработке AoS?
4. Для какого типа нагрузки вариант AoS может оказаться предпочтительнее SoA? Приведите пример доступа к данным, при котором это возможно.

# Задача B. Вне конкуренции

#### Этап 1. Воспроизведение false sharing

Реализуйте два потока. Каждый поток должен увеличивать собственный счётчик типа `uint64` или атомарный счётчик достаточно большое (~100 миллионов на современных машинах, покрутите вверх если не получается или вниз если программа работает долго) количество раз.

Сравните два варианта размещения счётчиков:

- **Вариант A:** оба счётчика расположены рядом в одной структуре и попадают в одну кэш-линию.
- **Вариант B:** каждый счётчик дополнен padding так, чтобы располагаться в собственной 64-байтовой кэш-линии.

```c
// Зафиксируйте размер кэш-линии своей платформы или используйте std::hardware_destructive_interference_size
constexpr std::size_t CACHE_LINE_SIZE = 64

// Два счётчика расположены рядом.
struct AdjacentCounters {
    std::atomic<std::uint64_t> counters[2]{};
};

// Каждый счётчик выровнен на отдельную кэш-линию.
struct alignas(CACHE_LINE_SIZE) PaddedCounter {
    std::atomic<std::uint64_t> value{0};
};
```

Измерьте время выполнения обоих вариантов и вычислите ускорение варианта B относительно варианта A.

*Замечание:* в Linux закрепите потоки за разными ядрами с помощью `taskset -c 0,1`, чтобы планировщик ОС не запускал их последовательно на одном ядре и не скрывал эффект конкуренции.

**Вопросы:**
1. Какое время выполнения показал каждый вариант? Во сколько раз вариант B быстрее или медленнее варианта A?
2. Подтвердили ли вы, что потоки выполнялись на разных ядрах? Как именно?
3. Почему вариант A может работать медленно, если потоки изменяют разные счётчики и не обращаются к данным друг друга?
4. Как, по вашему прогнозу, изменение числа потоков повлияет на проблему в варианте A? Почему?

#### Этап 2. Поиск false sharing с помощью `perf c2c`

Возьмите невыровненную (медленную) версию программы из этапа 1. 

Запишите профиль выполнения и сформируйте отчёт:

```bash
perf c2c record -- ./bench
perf c2c report --stdio
```

В отчёте найдите кэш-линию с наибольшим значением `remote HITM`. Определите два байтовых смещения, в которые записывают разные CPU, и сопоставьте эти смещения с полями структуры. 

**Вопросы:**
1. В какой кэш-линии отчёт показывает наибольшую конкуренцию?
2. Как результаты `perf c2c` подтверждают или опровергают выводы, сделанные по времени выполнения на этапе 1?

*Подсказка:* ищите таблицу `Shared Data Cache Line Table` и детализацию `Cacheline` для соответствующей строки. Высокое значение `Rmt HITM` (`remote hit-on-modified`) указывает на конкуренцию ядер за одну и ту же кэш-линию. 

*Подсказка:* если данных недостаточно, увеличьте продолжительность выполнения или частоту. Закрепите потоки за разными ядрами, чтобы конкуренция была воспроизводимой.
