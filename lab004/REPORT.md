## Этап 1. Упаковка структур и выравнивание полей

*код для этого этапа лежит в файле [1.cpp](./1.cpp)*

`Mixed` - структура в обычном виде, `MixedP` - струтура с принудительной упаковкой (я переименовала чтобы все писть в 1 файле)

Размер обеих структур:

sizeof(Mixed) = 32
alignof(Mixed) = 8
sizeof(MixedP) = 16
alignof(MixedP) = 1

1. Размер обычной структуры - 32, упакованной - 16.  Да, размер упакованной структуры совпадает с суммой размеров её полей, тк при упаковке типы данных располагаются в памяти с помощью жадного алгоритма

2. При попытке взять адрес предупреждение или сообщение об ошибке не было получено. Компилятор предполагает, что объект в памяти выровнен по 4 байта и эсли это не так, то компилятор демонстрирует неопределённое поведение

## Этап 2. AoS и SoA

*код для этого этапа лежит в файле [2.cpp](./2.cpp)*

1.  AoS: 107.9 ms
    SoA: 99.8 ms
    SoA быстрее в 1.08 раза (на 8.1 ms)

2.  В кэш-линии 64 байта.
    - **AoS:** 4*6 = 24 полезных байта, 4 бесполезных от `color` => в линию помещается `64 / 28 = 2.28` частицы. Полезно из линии: `x,vx,y,vy,z,vz` - 24 байта на частицу, но `color` (4 байта) неизбежно попадает в кэш вместе с нужными полями. 28 не делит 64 => часть частиц рвётся между двумя линиями, добавляя лишние обращения. Тогда ~55 из 64 байт полезны
    
    - **SoA:** каждое поле — отдельный выровненный массив 4-байтовых элементов => в линию помещается **ровно 16 элементов** одного поля. Шаг трогает только `x, vx, y, vy, z, vz`, `color` вообще не загружается. => нет разорванных элементов, тк 64 делится на 4 нацело. Тогда 64 из 64 байт полезны

3. В SoA данные каждого поля хранятся в отдельном массиве => элементы одного массива расположены последовательно в памяти. Компилятору проще загружать сразу несколько однотипных значений в SIMD-регистр и выполнять над ними одну операцию параллельно. В то время как в AoS данные разных полей одной структуры хранятся вместе => для обработки одного конкретного поля приходится пропускать остальные поля, что усложняет загрузку данных в SIMD-регистры и может потребовать дополнительных операций перестановки.

4. AoS предпочтительнее SoA при нагрузках, в которых часто требуется обращаться ко всем полям одной структуры одновременно. Например, структура описывает точку, в которой находится объект. В ней хранятся 3 координаты, и объект может двигаться в любом направлении:

  ```cpp
    struct Particle {
    float x;
    float y;
    float z;
  };
  ```
Тогда при движении объектов AoS будет удобнее для одновременного изменения координат каждого объекта

# Задача B. Вне конкуренции

## Этап 1. Воспроизведение false sharing

*код для этого этапа лежит в файле [bench.cpp](./bench.cpp)*

1. 

```
  Variant A
  Thread 1 CPU: 0
  Thread 2 CPU: 1
  Counter 1: 100000000
  Counter 2: 100000000
  Time A: 5.71463 seconds

  Variant B
  Thread 1 CPU: 0
  Thread 2 CPU: 1
  Counter 1: 100000000
  Counter 2: 100000000
  Time B: 1.13956 seconds

  Speedup (A / B): 5.01478
```

2. Да, подтвердила я вывела результат функции sched_getcpu()
3. Всё из-за False Sharing. Несмотря на то, что потоки изменяют разные переменные, эти переменные находятся в одной кэш-линии. При записи одного потока кэш-линия становится недействительной или должна передаваться другому ядру. Поэтому ядра постоянно обмениваются этой кэш-линией => возникает конкуренция за доступ к кэш-линии, хотя потоки логически работают с независимыми счётчиками.
4. При увеличении количества потоков проблема False Sharing может усилиться, поскольку большее количество ядер будет конкурировать за одну кэш-линию. Это увеличит количество передач кэш-линий между ядрами и может снизить производительность.
